## 0. The decisions in one screen

| Topic | Decision |
|---|---|
| Place identity | One `places` table. `source=osm` rows are canonical, unique on `(osm_type, osm_id)`, and carry reviews. `source=custom` rows belong to one trip (`trip_id`) and die with it. CHECK enforces the two shapes. |
| Trip content | `trip_places` (place in trip + private note) → `stops` (trip place on a day, ordered). A trip place with no stops is an "idea". The same trip place may appear on several days (the hotel). |
| Same-trip integrity | `stops` has a denormalised `trip_id` and two composite FKs, `(day_id, trip_id)` → `days(id, trip_id)` and `(trip_place_id, trip_id)` → `trip_places(id, trip_id)`. The database rejects a stop that mixes trips **[RAN]**. |
| Ordering | Dense integer `position` per day. Every structural write locks the trip row with one `UPDATE trips SET plan_version = plan_version + 1 WHERE id = $1 AND owner_id = $2 RETURNING plan_version`, then rewrites whole day orders with a two-phase update. Full-list writes are checked for membership (409 on mismatch). Clients send no version. |
| Planner read | `GET /api/v1/trips/{tripId}/plan`: trip, all trip places with place summaries and rating summaries, days with ordered stops, cached route summaries. Six fixed queries, no provider call. |
| Routes | `GET /api/v1/trips/{tripId}/days/{dayId}/route`, per-leg cache in `provider_cache` with content-addressed keys (coordinates + mode + provider), so no invalidation code exists. The client keys the query by `planVersion`. |
| Auth | 32-byte random token, SHA-256 stored as `bytea`, cookie `__Host-hm_session` (prod) / `hm_session` (dev), 30-day idle sliding window touched at most hourly, 90-day absolute cap. Argon2id via `@node-rs/argon2` 2.2.2. Origin / Sec-Fetch-Site check on every unsafe method. |
| Contract plumbing | One endpoint table in `packages/shared/src/api/endpoints.ts` drives Nest routing (an `@Endpoint()` decorator), input validation (a global interceptor), output allowlisting (the same interceptor parses responses), the OpenAPI 3.1 document (`zod-openapi` 6.0.2) and the web client's typed fetcher. |
| Paths | No `:verb` suffixes: Express 5 uses path-to-regexp 8.4.2, where `:` starts a parameter. Non-CRUD actions are nouns: `POST /trips/{id}/copies`, `PUT /trips/{id}/stops/{stopId}/placement`, `DELETE /sessions/current`. |
| Guest drafts | Cut from v1 **[J]**: a browser-only draft needs a second, client-side implementation of every plan mutation plus an import endpoint. Guests browse Explore, public trips and place pages; sign-up is three fields and returns to where they were. Lead may override. |

## 1. Domain model

### 1.1 Prisma schema (`apps/api/prisma/schema.prisma`)

Follows the skeleton: `prisma-client` generator into `src/generated/prisma`, URL from `prisma7.config.ts`, snake_case tables and columns, `timestamptz(3)`. Two changes from the placeholder: ids default to PostgreSQL 18's native `uuidv7()` (`dbgenerated`) instead of Prisma's client-side `uuid(7)`, because the trip copy is an `INSERT … SELECT` in raw SQL that must get ids from the database; and the `partialIndexes` preview feature (present in 7.10.1's schema engine **[RAN]**, it rendered `CREATE INDEX … WHERE (…)`) for the discovery indexes.

/// A place collected into a trip, with the traveller's private note.
/// A trip place with no stops is an "idea" (unscheduled).
model TripPlace {
  id        String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  tripId    String   @map("trip_id") @db.Uuid
  trip      Trip     @relation(fields: [tripId], references: [id], onDelete: Cascade)
  placeId   String   @map("place_id") @db.Uuid

  /// still works: it cascades to its trip_places and its custom places in one statement
  /// (measured on PostgreSQL 18.7).
  place     Place    @relation(fields: [placeId], references: [id], onDelete: Restrict)
  note      String?  @db.VarChar(4000)
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  updatedAt DateTime @updatedAt @map("updated_at") @db.Timestamptz(3)

  stops Stop[]

  @@unique([tripId, placeId])
  /// Target of the composite FK from stops, so a stop cannot point into another trip.
  @@unique([id, tripId])
  @@index([placeId])
  @@map("trip_places")
}

### 1.2 Hand-written SQL appended to the first domain migration

Prisma cannot express CHECK constraints. Create the migration with `prisma migrate dev --create-only`, append this block, then apply. Prisma's diff does not model CHECKs and, per its docs, leaves them in place on later `migrate dev` runs (I did not run a second migration to watch it); a migration test (bug 10) proves they exist.

```sql
-- Appended by hand to the generated migration (prisma migrate dev --create-only, then edit).
ALTER TABLE places ADD CONSTRAINT places_source_shape_chk CHECK (
  (source = 'osm' AND osm_type IS NOT NULL AND osm_id IS NOT NULL AND trip_id IS NULL)
  OR (source = 'custom' AND osm_type IS NULL AND osm_id IS NULL AND trip_id IS NOT NULL));
ALTER TABLE places ADD CONSTRAINT places_lng_lat_chk CHECK (lng BETWEEN -180 AND 180 AND lat BETWEEN -90 AND 90);
ALTER TABLE trips ADD CONSTRAINT trips_destination_point_chk CHECK ((destination_lng IS NULL) = (destination_lat IS NULL));
ALTER TABLE trips ADD CONSTRAINT trips_published_chk CHECK ((visibility = 'public') = (published_at IS NOT NULL));
ALTER TABLE trips ADD CONSTRAINT trips_share_token_chk CHECK (visibility = 'private' OR share_token IS NOT NULL);
ALTER TABLE trips ADD CONSTRAINT trips_plan_version_chk CHECK (plan_version >= 0);
ALTER TABLE days ADD CONSTRAINT days_position_chk CHECK (position >= 0);
ALTER TABLE stops ADD CONSTRAINT stops_position_chk CHECK (position >= 0);
ALTER TABLE reviews ADD CONSTRAINT reviews_rating_chk CHECK (rating BETWEEN 1 AND 5);
ALTER TABLE reviews ADD CONSTRAINT reviews_visited_on_chk CHECK (visited_on IS NULL OR extract(day FROM visited_on) = 1);
ALTER TABLE reviews ADD CONSTRAINT reviews_hidden_chk CHECK ((status = 'hidden') = (hidden_at IS NOT NULL));
ALTER TABLE reports ADD CONSTRAINT reports_target_chk CHECK (
  (target_type = 'review' AND review_id IS NOT NULL AND trip_id IS NULL AND reported_user_id IS NULL)
  OR (target_type = 'trip' AND trip_id IS NOT NULL AND review_id IS NULL AND reported_user_id IS NULL)
  OR (target_type = 'user' AND reported_user_id IS NOT NULL AND review_id IS NULL AND trip_id IS NULL));
ALTER TABLE user_blocks ADD CONSTRAINT user_blocks_not_self_chk CHECK (blocker_id <> blocked_id);
```

Probe results **[RAN]** on PostgreSQL 18.7: an osm row with a `trip_id` → `violates check constraint "places_source_shape_chk"`; a stop in trip A's day pointing at trip B's trip place → `violates foreign key constraint "stops_trip_place_id_trip_id_fkey"`; `visibility='public'` without `published_at` → `violates check constraint "trips_published_chk"`; deleting a trip that has a custom place, trip places and stops → `DELETE 1`, leaving 0 stops and only the other trip's rows (works with RESTRICT on `trip_places.place_id`); deleting a canonical place still used by a trip → `violates RESTRICT setting of foreign key constraint "trip_places_place_id_fkey"`.

### 1.3 Model notes

- **Users.** `email` is stored lower-cased and trimmed (service-side `normalizeEmail`); no `citext` extension needed. `role` exists only for the moderation queue; a moderator is created by the seed or by SQL, never through the API.
- **Destination is not a Place.** A trip's destination is a label, a country code (for discovery filtering) and a centre for an empty map. Making it a `places` row would put cities into the reviewable set.
- **Custom pins are per trip.** Following the providers brief, custom pins live in `places` (`osm_*` NULL) so every trip place has the same shape (`trip_place.place`). Unlike the brief's sketch, they carry `trip_id`: renaming a pin in your trip can never rename it in someone's copy, a copy clones the row, and a trip delete removes it. Reviews require `source = osm`.
- **Notes are private by default.** `trip_places.note` is the owner's. `trips.share_notes` (default false) decides whether link and public views show them (UX: Polarsteps keeps planning notes private; principle 9).
- **Dates.** `start_date` is optional; day *n*'s date is derived. Non-owners never receive `startDate` or day dates, only `durationDays` and, for public trips, `publishedAt` (UX principle 9: "public trips hide exact dates").
- **Ratings are computed on read**, not denormalised: `SELECT place_id, count(*), sum(rating), count(*) FILTER (WHERE rating = n)… FROM reviews WHERE place_id = ANY($1) AND status = 'published' GROUP BY place_id` on the `(place_id, status, …)` index. A planner holds at most 300 places, so one grouped query; no counter can drift.
- **Visibility `link`** = readable by anyone with the share token, never listed. `public` = listed in discovery and on the author's profile, also readable by id. Both require a share token (CHECK), so a public trip turned back into `link` keeps working links.

### 1.4 Invariants the database cannot express

| # | Invariant | Enforced in | Test |
|---|---|---|---|
| I1 | `days.position` and `stops.position` are dense `0..n-1` (UNIQUE only prevents duplicates) | `PlanOrderWriter.writeDayOrder`, the single function that writes positions | property test: random sequence of plan operations, assert density after each |
| I2 | A day holds at most 25 stops; a trip at most 60 days, 300 trip places; a user at most 100 trips | `PlanService` inside the trip lock (counts read after the lock) | boundary tests at 25/26, 60/61 |
| I3 | Reviews only on `source = osm` places | `ReviewsService.upsert` (404 `place_not_found` for custom ids, so custom pins stay invisible) | integration test |
| I4 | A custom place is referenced only by trip places of its own trip | `PlanService.addTripPlace` creates the custom place and the trip place together; no endpoint takes a custom place id | integration test via copy |
| I5 | `trips.plan_version` increases on every change that alters stops, days, trip places, leg modes or custom-pin coordinates | `PlanService` (every structural method starts with `lockPlan`) | test per mutation: version strictly increases |
| I6 | Report auto-hide: a review with 3 open reports from distinct reporters becomes `hidden` | `ReportsService.create`, same transaction, after the insert | integration test |
| I7 | Non-owners never see `startDate`, day dates, `shareToken`, or notes unless `shareNotes` | separate output schemas (`tripPublicSchema` has no such fields) parsed by the contract interceptor | contract test on the public views |
| I8 | Blocked users' reviews and trips are hidden from the blocker | `WHERE author_id NOT IN (SELECT blocked_id FROM user_blocks WHERE blocker_id = $viewer)` in the review and discovery queries | integration test |
| I9 | `places` rows are never updated from client input | the only writer is `PlacesService.upsertCanonical(ref)` resolving from cache or Nominatim `/lookup` | test: client-sent name ignored |

## 2. Ordering stops

### 2.1 Options

| | A. Dense integers + whole-day rewrite under a trip lock | B. Fractional keys (LexoRank / `fractional-indexing` 4.0.0) | C. `uuid[]` order column on `days` |
|---|---|---|---|
| Write cost of a move | Rewrites the 1-2 affected days: ≤ 50 rows, two statements per day | One row | One or two rows |
| Concurrent writes from two tabs | Serialised by the trip row lock; preconditions checked after the lock | Two inserts between the same neighbours generate the same key: needs a tie-break column or retry; keys grow without rebalancing | Serialised by the day row, but element integrity is not enforced by any FK |
| Referential integrity | Full (FKs on stops) | Full | None for array elements: a deleted trip place leaves a dangling id unless every delete edits the array |
| Testing | Positions are `0..n-1`: assert arrays | Must assert ordering of opaque strings, plus rebalancing | Easy to assert, hard to keep consistent |
| Reading | `ORDER BY position` | `ORDER BY rank COLLATE "C"` (collation trap) | `unnest … WITH ORDINALITY` join |

**Pick A.** A day's list is capped at 25 stops (the routing cap from the providers brief), so B's single-row advantage buys nothing, and C gives up the FK protection that section 1.1 relies on.

### 2.2 The mechanism

1. **One lock statement starts every structural write** (`PlanService.lockPlan(tx, tripId, userId)`):
   ```sql
   UPDATE trips SET plan_version = plan_version + 1, updated_at = now()
   WHERE id = $1 AND owner_id = $2 RETURNING plan_version
   ```
   0 rows → 404 `trip_not_found` (covers "someone else's trip"). It scopes by owner, takes the row lock that serialises the trip's writers, and bumps the version, all at once. **[RAN]** two sessions issued it for the same trip: the second waited until the first committed (about 1 s in the probe) and then updated 0 rows because it carried a stale `plan_version = 5` predicate; without that predicate it simply proceeds after the first commits, which is the behaviour we use.
2. **Preconditions are checked after the lock**, on fresh data: stop ids belong to the day, the list is a permutation of the day's current stops, limits.
3. **Positions are written by one function**, `writeDayOrder(tx, dayId, orderedStopIds)`:
   ```sql
   UPDATE stops SET position = position + 1000 WHERE day_id = $1;
   UPDATE stops s SET position = v.ord - 1
   FROM unnest($2::uuid[]) WITH ORDINALITY AS v(id, ord)
   WHERE s.id = v.id AND s.day_id = $1;
   ```
   **[RAN]** A one-statement permutation (`UPDATE … FROM (VALUES …)`) and a one-statement shift (`position = position + 1`) both fail with `duplicate key value violates unique constraint "stops_day_id_position_key"`: PostgreSQL checks a non-deferrable UNIQUE row by row. Prisma cannot declare a DEFERRABLE constraint, and a negative offset violates `stops_position_chk`, so the offset is `+1000` (above the 25-stop cap). The two-phase version produced positions 0, 1, 2 in the requested order. Days use the same function on `days.position`.
4. **No client version.** The client never sends `planVersion`. Single-item operations (move one stop to day X index i, append, remove) are valid against any current state: the index is clamped to `[0, n]`. Full-list operations (`stop-order`, `day-order`) must name exactly the current members, otherwise 409 `plan_changed` with the current `planVersion` in the problem body; the client refetches and the user retries. Two tabs therefore never corrupt order; the last writer wins on position, and a stale full list is refused instead of silently dropping a stop.
5. **Every structural response** returns `{ planVersion }` (plus the created entity on 201). The client invalidates `['trips', tripId, 'plan']`.

### 2.3 Client contract for optimistic reordering

- `useMutation({ scope: { id: \`plan:${tripId}\` } })` for every plan mutation: TanStack Query 5.108 has `MutationOptions.scope` **[SRC]**, which runs mutations with the same scope id one after another, so two quick drags reach the server in order.
- `onMutate`: cancel `['trips', tripId, 'plan']` queries, snapshot, apply the move to the cached plan. `onError`: restore the snapshot, toast "Não foi possível mover. Desfazer" with the problem `detail`. `onSettled`: invalidate the plan query.
- Undo = the inverse mutation (move back to the old day and index; re-add a removed trip place with its note, which the client kept from the snapshot).
- Drag and the tap twin ("Move to day", "Move up/down") call the same two endpoints.

## 3. Authentication

### 3.1 Sessions

- **Token**: `crypto.randomBytes(32).toString('base64url')` (43 chars). Stored: `sha256(token)` as `bytea` in `sessions.token_hash` (UNIQUE). Lookup is by hash, so there is no comparison to make constant-time; a database leak gives no usable cookie.
- **Cookie**: name `__Host-hm_session` when `NODE_ENV=production` (the prefix forces `Secure`, `Path=/`, no `Domain`), `hm_session` in development (plain http on localhost). Attributes: `HttpOnly; SameSite=Lax; Path=/; Max-Age=<seconds to expiresAt>`. Set only by the API; Next's rewrite passes `Set-Cookie` through to the browser.
- **Lifetimes**: idle 30 days, absolute 90 days. On each authenticated request the guard loads `SELECT … FROM sessions JOIN users … WHERE token_hash = $1 AND expires_at > now() AND absolute_expires_at > now()`. If `last_used_at < now() - 1 h` it updates `last_used_at = now(), expires_at = least(now() + 30 d, absolute_expires_at)` and re-sends the cookie with the new `Max-Age`. Touching at most hourly keeps reads read-only.
- **Server Components** forward the incoming `Cookie` header to the API (`API_URL` server-to-server). A Set-Cookie on those responses is dropped by Next (RSC cannot set cookies), which is fine: browser-side TanStack Query calls through `/api/*` refresh the cookie. Server-to-server calls only use GET, so the CSRF check never sees them.
- **Logout**: `DELETE /api/v1/sessions/current` deletes the row and sends `Max-Age=0`. **Logout everywhere**: `DELETE /api/v1/sessions` deletes all the user's rows, including the current one.
- **Purge**: an hourly in-process job deletes expired sessions in batches of 1,000 (and expired `provider_cache` rows, as the brief requires).

### 3.2 CSRF (`CsrfGuard`, global, runs first)

For `POST`, `PUT`, `PATCH`, `DELETE` on any path:
1. If `Sec-Fetch-Site` is present, it must be `same-origin`. (`same-site` is refused too: another app on a sibling localhost port is same-site.)
2. Else `Origin` must be present and equal `WEB_ORIGIN` exactly (`http://localhost:3100` in dev).
3. Else 403 `csrf_rejected`.
4. Bodies must be `Content-Type: application/json` (415 `unsupported_media_type`), which rules out HTML form posts as a second line.

This applies to sign-up and login too (login CSRF). Not verified: that Next 16's rewrite proxy forwards `Origin` and `Sec-Fetch-Site` unchanged; an e2e test through port 3100 must cover it (bug 4).

### 3.3 Passwords and limits

- Argon2id with `@node-rs/argon2` 2.2.2 (`memoryCost: 19456` KiB, `timeCost: 2`, `parallelism: 1`). Its `Algorithm` is a `const enum` in an ambient `.d.ts` **[SRC]**, unusable under the skeleton's `isolatedModules`; Argon2id is its documented default, so omit `algorithm` and assert `$argon2id$v=19$m=19456,t=2,p=1$` in a unit test. Chosen over `argon2` 0.45.2 because it ships prebuilt binaries as optional dependencies and needs no entry in pnpm's `allowBuilds`.
- Password rules: 10 to 128 characters (`z.string().min(10).max(128)`), no composition rules, paste allowed.
- Unknown e-mail at login still runs `verify` against a fixed dummy hash, so timing does not reveal accounts. Response: 401 `invalid_credentials` in both cases.
- **Login limits**: per IP 10 per minute (throttler `auth`); per normalised e-mail, 5 failures in 15 minutes → 429 `too_many_attempts` with `Retry-After` until the window ends (in-process `LoginAttemptService`, cleared on success). No account lockout, which would let anyone lock out a victim.
- **Sign-up limits**: 5 per IP per hour. Duplicate e-mail → 409 `email_taken`. That reveals which e-mails have accounts; with no e-mail delivery in v1 there is no "check your inbox" flow to hide it behind. Accepted risk, owner: project owner.
- `// SHORTCUT(owner): login, sign-up and request rate counters live in the API process — ceiling: one API instance; upgrade: before a second instance runs, move them to a shared store` (same ceiling as the provider token buckets).
- **Password change**: `PUT /api/v1/me/password { currentPassword, newPassword }`. Verifies the current one, rehashes, sets `password_changed_at`, deletes every other session, and rotates the current one (new token, new cookie).
- **Account deletion**: `DELETE /api/v1/me` with body `{ password }`. One transaction deletes the user; cascades remove sessions, trips (public ones included, so their pages answer 404), trip places, stops, custom places, reviews (rating summaries are computed on read, so they update at once), blocks, and reports against them. Reports the user filed survive with `reporter_id = NULL`. Copies other people made of the user's public trips survive: a copy is a deep copy and `copied_from_trip_id` becomes NULL. The UI warns that public trips and reviews disappear. Anonymising reviews instead was rejected: a rating with no accountable author is the opposite of what makes reviews trustworthy, and erasure is what a departing user expects.

### 4.3 The planner in very few requests

- **Server Component, one request**: `GET /trips/{tripId}/plan` → `TripPlan`. The API runs five queries: (1) trip + author with access check; (2) trip places joined to places; (3) days; (4) stops ordered by `(day position, position)`; (5) one grouped review aggregate over the place ids. Then a sixth over `provider_cache` with `key = ANY($legKeys)` for the route summaries. No provider call, so the page never waits on OSRM.
- **Client**: TanStack Query hydrates `['trips', tripId, 'plan']` from the server payload (`staleTime: 30 s`). For each day whose summary has a `null` leg and that is visible (selected day chip, or "All"), it fetches `['trips', tripId, 'route', dayId, planVersion]` with `staleTime: Infinity`; the key changes whenever the plan does, and unchanged legs come back from the cache in milliseconds.
- **Search and place pages** are separate queries; they are not on the planner's critical path.

### 4.5 Error codes

`type` = `urn:heremita:problem:<code>`; `title` = a fixed English phrase per code; `detail` = human text; `instance` = request path; `code` = the stable member below. Validation failures are 422 `validation_failed` with `errors[{ pointer, detail }]`, where `pointer` is a JSON Pointer rooted at the part of the request: `/body/stopIds/3`, `/query/limit`. Malformed JSON → 400 `malformed_request`. A malformed path id is a 404 of that resource (a non-UUID cannot exist).

| Status | Codes |
|---|---|
| 400 | `malformed_request` |
| 401 | `unauthenticated`, `invalid_credentials` |
| 403 | `csrf_rejected`, `wrong_password`, `forbidden` (moderation only; ownership failures are 404) |

## 5. Authorisation matrix

Owner = `trips.owner_id` is the session user. Viewer access to a trip = `visibility = public` (and not moderation-hidden), or `visibility = link` with the right token. Everything else is a 404, never a 403 (standards 3.1).

| Resource / action | Anonymous | Signed-in non-owner | Owner |
|---|---|---|---|
| Discovery list, user profile, user's public trips and reviews | read | read (minus users they blocked) | read |
| Trip header and plan (#16, #21), day route (#35) | viewer access only; no dates, no share token, notes only if `shareNotes` | same | full |
| Trip edits, share token, delete, all plan mutations, order suggestion | 404 / 401 | 404 | yes |
| Copy a trip (#22) | 401 | with viewer access | yes (duplicate) |
| Place detail and reviews of an osm place | read | read (minus blocked authors) | n/a |
| Custom place | 404 | 404 | only through its trip |
| Write / replace / delete a review | 401 | own review only (`/reviews/mine`, never by review id) | n/a |
| Report | 401 | any review, public/link trip they can see, or user; not their own | n/a |

## 6. Geocoding and routing through the API

Everything below follows the providers brief (sections 2, 4, 7); this section only adds where it meets the domain model.

### 6.1 What is stored where

| Data | Where | Key | TTL / life |
|---|---|---|---|
| Photon search, reverse; Nominatim search, lookup | `provider_cache` | upstream URL (brief 7.4) | 24 h (1 h if empty) / 7 d / 24 h / 30 d |
| A place served to a client in search or reverse | `provider_cache` | `place:v1:osm:W:1370081491` → `PlaceResult` | 24 h |
| A place someone saved | `places` (permanent) | `UNIQUE (osm_type, osm_id)` | forever; `last_seen_at` refreshed on each re-serve |
| One route leg | `provider_cache` | `leg:v1:{provider}:{mode}:{lng5},{lat5}>{lng5},{lat5}` → `{ distanceMeters, durationSeconds, polyline, snapped }` | 7 d |
| Estimates and errors | nowhere | | |
| Day route response | not stored; assembled from legs | ETag = sha256 of the leg keys + quality | |

Saving (#23): the server takes only `key`, reads `place:v1:<key>` from the cache; on a miss (expired, or a forged key) it calls Nominatim `/lookup` once (1 token per 1.1 s, brief 7.5); if that fails, 503 `geocoding_unavailable` and nothing is written. Client-sent names and coordinates for osm places are never stored (I9).

### 6.2 Route computation (`RouteService.dayRoute`)

1. Access check (`TripAccessService`), then load the day's stops with coordinates and effective modes (`stop.modeToNext ?? day.modeOverride ?? trip.defaultMode`).
2. Build the legs `(stop i → stop i+1, mode)`, their keys, and fetch them all with one `SELECT key, value FROM provider_cache WHERE key = ANY($1) AND expires_at > now()`.
3. Group uncached legs into maximal runs of consecutive legs with the same mode; one OSRM `/route` call per run (2-25 coordinates), through the brief's token bucket (1 req/s, burst 1), timeout 6 s, request deadline 8 s.
4. Split each response into legs at the snapped waypoints (`routeFromOsrm`), apply the snap rule (1,000 m walk/bike, 3,000 m drive → `unroutable`, estimated leg), and upsert routed legs with `INSERT … ON CONFLICT (key) DO UPDATE` after the response, outside any transaction.
5. Legs whose run failed or waited past 3 s for a token become straight-line estimates (brief 7.7), `estimated: true`, never cached. `quality` = `routed` if none estimated, `estimated` if all, else `partial`.

**Invalidation needs no code.** A leg key is a function of its endpoints' coordinates, its mode and the provider, so moving, inserting or removing a stop produces new keys for the affected legs and old ones age out after 7 days. The client side follows the same idea: route queries are keyed by `planVersion`, which every change that can alter a route bumps (I5: stop moves, leg mode, day mode, custom-pin location, trip default mode). Renaming a place or editing a note does not bump it.

**Planner summaries** (#21) run steps 1-2 only and report `null` legs for misses, so the planner never waits on a provider.

**Order suggestion** (#36): straight-line matrix → `optimiseOrder` (brief 4.5, Held-Karp up to 12 free stops) with the first stop fixed and the last fixed when `keepLast`; then the route for the suggested order through steps 2-5 so `after` is real where possible (`estimated: true` otherwise). It writes nothing; the client applies it with #31 and keeps the old order for Undo.

### 6.3 Client-facing limits (throttler, per user id or IP)

The brief's token buckets (search 5/s burst 10, reverse 1/s burst 3, route 2/s burst 5) become `@nestjs/throttler` fixed windows: search 10 per 2 s, reverse 3 per 3 s, route and order-suggestion 5 per 2.5 s; sign-in 10 per minute per IP; sign-up 5 per hour per IP; everything else 120 per minute. The throttler keys counters by tracker plus controller and handler **[SRC: `generateKey`]**, so each limit is per endpoint. Search answers carry `Cache-Control: private, max-age=300`.

### 7.2 One endpoint table drives routing, validation, OpenAPI and the client

```ts
// packages/shared/src/api/endpoints.ts
export const endpoint = <const E extends EndpointDef>(e: E) => e;
export interface EndpointDef {
  method: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';
  path: `/${string}`;                       // OpenAPI style: /trips/{tripId}/plan
  auth: 'none' | 'optional' | 'required' | 'moderator';
  params?: z.ZodObject; query?: z.ZodType; body?: z.ZodType;
  status: 200 | 201 | 204; response?: z.ZodType;
  throttle?: 'search' | 'reverse' | 'route' | 'auth' | 'signup';
  errors: readonly ErrorCode[];             // documented in OpenAPI; tested in bug 9
}
export const endpoints = {
  getTripPlan: endpoint({ method: 'GET', path: '/trips/{tripId}/plan', auth: 'optional',
    params: z.object({ tripId: idSchema }), query: z.object({ shareToken: z.string().max(32).optional() }),
    status: 200, response: tripPlanSchema, errors: ['trip_not_found'] }),
  putStopOrder: endpoint({ method: 'PUT', path: '/trips/{tripId}/days/{dayId}/stop-order', auth: 'required',
    params: z.object({ tripId: idSchema, dayId: idSchema }), body: stopOrderBodySchema,
    status: 200, response: planChangeSchema, errors: ['trip_not_found', 'not_found', 'plan_changed'] }),
  // … one entry per row of 4.4
} as const;
```

- **API**: `@Endpoint(endpoints.putStopOrder)` = `applyDecorators(Put('trips/:tripId/days/:dayId/stop-order'), HttpCode(200), SetMetadata(ENDPOINT, def), Throttle(...))`. The handler signature is `(@Input() input: EndpointInput<typeof endpoints.putStopOrder>, @CurrentUser() user: SessionUser)`.
- **Validation**: a global `ContractInterceptor` reads the metadata, parses `req.params` (failure → 404 of the resource), `req.query` and `req.body` (failure → 422 `validation_failed`, pointers `/query/...`, `/body/...`), and stores the result on `req.contract` for `@Input()`. Express 5's `req.query` is a getter **[SRC: express 5.3.0 `lib/request.js:230`]**, so parsed values cannot be written back. The same interceptor `map`s the handler result through `def.response.parse` (strip unknown keys); a failure there is our bug: logged at `error`, answered as 500. An interceptor rather than a pipe because a pipe sees one argument at a time and cannot apply the response schema or know the endpoint's status code.
- **Why not a library**: `nestjs-zod` 5.6.0 declares `@nestjs/common ^10 || ^11` and `@nestjs/swagger` 7-11 as peers **[npm view]**, so it does not support Nest 12; `@nestjs/swagger` 12.1.2 needs `class-validator`/`class-transformer`. The interceptor is about 60 lines.
- **OpenAPI**: `document.ts` maps `endpoints` to `createDocument({ openapi: '3.1.0', … })` from `zod-openapi` 6.0.2 (peer `zod ^4.0.0`), path params into `requestParams.path`, query into `requestParams.query`, body into `requestBody`, `def.errors` into problem responses (`application/problem+json`, schema `problemDetailsSchema`). Served at #2; a test writes it to `apps/api/openapi.json` and fails on drift, so the file in git is always generated.
- **Web client**: `apiFetch(endpoints.putStopOrder, { params, body })` builds the URL from `path`, sends JSON, throws `ApiError(problemDetailsSchema.parse(body))` when `!res.ok`, and returns the body typed as `z.infer<typeof def.response>` without parsing it (lead decision 3).
- **Route-table test**: Nest's `DiscoveryService` lists controller methods with `ENDPOINT` metadata; the set must equal `Object.values(endpoints)`. A handler without `@Endpoint` fails the test.

### 7.3 Exception filter

Extend the skeleton's `ProblemDetailsFilter`:
- `ApiProblem extends HttpException` carries `code`, `detail`, `extensions` (`currentPlanVersion`, `tripPlaceId`) and optional `retryAfterSeconds`; the filter writes `type: urn:heremita:problem:<code>`, the fixed title, `instance: request.originalUrl`, and `Retry-After`.
- `ThrottlerException` → 429 `rate_limited`, keeping the guard's `Retry-After` header. The guard writes a plain `Retry-After` only for the throttler named `default` and `Retry-After-<name>` for any other **[SRC: `throttler.guard.js:130-134`]**, which is why the design keeps a single `default` throttler and varies its limit per endpoint.
- Body-parser errors (`entity.parse.failed` → 400, `entity.too.large` → 413) and Prisma `P2002` on known constraints (`users_email_key` → 409 `email_taken`, `reviews_place_id_author_id_key` → handled in service) map explicitly; any other error → 500 `internal_error`, logged once with the request id.

### 7.4 Guards and decorators (registered as `APP_GUARD`, in this order)

1. `CsrfGuard` (3.2).
2. `SessionGuard`: reads the cookie, resolves and touches the session, sets `req.user`; then enforces `def.auth` (`required` → 401, `moderator` → 403). Runs before the throttler so the throttler can key by user.
3. `AppThrottlerGuard extends ThrottlerGuard` with `getTracker = req.user?.id ?? req.ip`. `app.set('trust proxy', TRUST_PROXY_HOPS)` so `req.ip` is the browser's address behind the Next rewrite. `ThrottlerModule.forRoot({ throttlers: [{ name: 'default', ttl: 60_000, limit: 120 }] })` (ttl in milliseconds **[SRC: README]**); per-endpoint values come from `@Throttle({ default: … })` set by `@Endpoint` from `def.throttle`, so each endpoint has one effective limit and no named throttler leaks onto every route.
- `@CurrentUser()` returns `req.user` (`{ id, role, locale, sessionId }`), typed non-null on `required` endpoints.
- `app.useBodyParser('json', { limit: '64kb' })`.
